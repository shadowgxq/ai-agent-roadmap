# W11–W12｜Agent Web Application → Coding Runtime & Sandbox

> W11：让 Agent Core 同时支持 CLI 和 Web，完成一个可用的 Agent Web Application。
>
> W12：在 Web Agent 之上增加 Workspace、Executor、Repository 和 Docker Sandbox，形成 Coding Agent Runtime。
>
> 两周约 20–30h，每个 Session 完成后暂停，等用户自行验收再进入下一个 Session。

## 1. 总体边界

```text
W10 Safety / Cost / Cache
        ↓
W11 Agent Web Application
        ↓
W12 Coding Runtime & Sandbox
        ↓
W13+ Planning / Long-horizon
```

本次不把 Web 产品化和 Docker 执行环境绑在一起：

- W11 先完成通用 Agent Web，可以使用现有本地工作区或受控运行器。
- W12 再抽象代码工作区、命令执行器和 Docker 隔离。
- 不新建第二套 Agent Loop、Next.js 工程或另一套 Web 协议。

核心模型：

```text
Agent Core
  ├── CLI Adapter
  └── Web Adapter
        └── Chat / Tool UI

Coding Agent
  └── Workspace → Executor → Sandbox
```

关键概念：

- Agent Core 负责 Context、LLM、工具编排、状态和事件；CLI/Web 只是 Adapter。
- Session 是一次对话，Run 是一次消息触发的完整 Agent Loop，Message 是单条 user/assistant/tool 记录。
- Event Protocol 是 Runtime 与 UI 的边界，使用 sequence、run_id、event、data。
- Workspace 管文件范围，Executor 管执行位置，Sandbox 管资源和权限隔离。

## 2. W11｜Agent Web Application

### W11 目标和调用链

```text
CLI:
cli.main
  → run_coding_agent
  → agent.loop.run
  → CLI Renderer

Web:
React
  → FastAPI
  → Session / Run Manager
  → Agent Runtime
  → Event Queue
  → SSE
  → React state
  → Chat / Tool UI
```

W11 结束时：CLI 不被破坏；Web 可以创建 Session、发送多轮消息、实时接收事件、展示 Tool Call/Result，并查看历史 Session。W11 不要求 Docker 完成。

### Session 03｜Structured Agent Events


再明确 diff、confirm_request、error、status 是否加入公共协议。tool_call 和 tool_result 必须通过同一个 tool_use_id 配对；compact_usage 等内部事件不能未经适配直接发送到前端。

文件：

验收：

- 每类公共事件都有字段说明和 JSON 示例。
- 非法事件类型不会静默进入 SSE。
- done 携带 completed、failed、max_turns 或 cancelled 等终态。
- Python 和 TypeScript 使用同一套事件命名。

## 3. W12｜Coding Runtime & Sandbox

### W12 目标和调用链

```text
Repository
  → Workspace
  → Agent Tool
  → Executor
  → Local / Docker Runtime
  → Structured Event
  → React Tool / Diff UI
```

W12 结束时：Agent 可以在抽象 Workspace 中操作代码；Executor 决定命令运行位置；Docker 提供隔离；文件修改可以形成 Diff；任务具有完整生命周期。

### Session 01｜Workspace Abstraction

目标：从 Path.cwd() 和工具内部路径拼接中抽离 Workspace，先实现 LocalWorkspace，明确 DockerWorkspace 的边界。

文件：

- agent-mini/src/tools/fs.py
- agent-mini/src/tools/search.py
- 新增 agent-mini/src/execution/workspace.py
- agent-mini/src/agent/runtime.py

验收：

- 文件工具不能越出 Workspace root。
- LocalWorkspace 可以替换当前直接使用的工作目录。
- Workspace 不负责执行任意 Shell。

### Session 02｜Execution Runtime

目标：抽象 Executor，先保持 LocalExecutor 行为，再准备 DockerExecutor。run_shell 只作为 Executor Adapter。

文件：

- agent-mini/src/tools/shell.py
- agent-mini/src/tools/policy.py
- agent-mini/src/agent/runtime.py
- agent-mini/src/agent/config.py
- 新增 agent-mini/src/execution/executor.py

验收：

- LocalExecutor 保持现有行为。
- 命令策略仍然先于执行器生效。
- on_confirm(command, reason) 可以映射到 confirm_request。
- Agent Loop 不依赖具体执行位置。

### Session 03｜Docker Sandbox

目标：通过 DockerExecutor 执行受控命令，限制 CPU、memory、PID、network、filesystem、timeout，并使用非 root 用户。

文件：

- 新增 agent-mini/src/execution/docker_executor.py

- agent-mini/src/tools/shell.py

验收：

- --network none、资源限制和 timeout 生效。
- 只挂载 Workspace，不挂载宿主敏感目录。
- 容器内使用非 root 用户。
- 正常命令可执行，读取宿主敏感文件和外发网络被隔离。
- 完成、失败、取消后容器能清理。

### Session 04｜Repository Workspace

## 4. Session 闸门与验证边界

每个 Session 都遵循：

```text
讲思路 → 读现有代码 → 用户确认 → 修改核心代码
→ 静态检查/单元或框架测试 → 用户自行验收
→ 再进入下一个 Session
```

验证规则：

- Python 改动：执行相应静态检查、导入/编译检查和相邻单元/框架测试。
- React/TypeScript 改动：执行受影响范围 ESLint、pnpm typecheck 和相邻 Vitest。
- 本文件只是学习计划变更：只做 git diff --check，不运行服务、全量测试或真实 LLM Eval。
- 真实 LLM Eval 默认不运行；如需运行，先说明 token/费用并等待明确要求。
- Git commit 不属于默认步骤。

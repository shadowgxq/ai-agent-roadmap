# W13｜LangChain / LangGraph 框架映射

> **一句话目标**：不再通过教程重学 Agent，而是把 `agent-mini` 已手写的 loop、tool、state、workflow 和 checkpoint 逐项映射到 LangChain v1 / LangGraph，建立企业强化项目 `support-agent/` 的最小骨架。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W1–W12 P0 验收通过，尤其是 W3 loop、W5 workflow、W6 checkpoint/subagent。

## 1. 核心要掌握

### 先确定框架的责任

- **LangChain v1** 是 model / tool / structured output / middleware 和预置 agent harness 的组合层。
- **LangGraph** 是低层状态编排 runtime，主要解决循环、分支、长任务、持久化、streaming 和 human-in-the-loop。
- LangChain `create_agent` 本身建在 LangGraph 上；业务流程有明确节点和审批时，直接使用 LangGraph，不把整个系统塞进一个预置 agent。

### 与手写实现建立一对一映射

| `agent-mini` 手写机制 | 框架对应 | 本周要回答的问题 |
|---|---|---|
| `while` agent loop | LangChain `create_agent` / LangGraph 循环边 | 终止条件和 `max_turns` 由谁控制？ |
| tool registry + Pydantic schema | LangChain `@tool` / tool schema | 工具异常、权限与结果截断放哪一层？ |
| `WorkflowState` | LangGraph typed state + reducer | 哪些值是 state，哪些是临时局部变量？ |
| router | conditional edge / `Command` | 路由是代码决策还是模型决策？ |
| evaluator-optimizer loop | 图中的 review 循环 | 怎么限制重试并保留评审状态？ |
| checkpoint JSON | checkpointer | 任务 state 与长期 memory 为什么不是一回事？ |
| subagent | subgraph / 受限 agent node | 什么时候子图是真实边界，什么时候只是过度抽象？ |
| event callback | `astream_events` + 应用事件适配层 | 为什么不能把框架原始事件直接当前端契约？ |

### State 是业务契约，不是临时变量篮子

- LangGraph state 必须可序列化，不放 SDK client、DB session、file handle 或 callback。
- 业务 state 使用 `TypedDict`；API DTO、structured output 与配置使用 Pydantic。
- 列表字段必须显式决定“覆盖”还是“追加”，只在确实需要聚合时使用 reducer。
- 不把完整文档、大段 tool output 或可以按 ID 重新查询的数据塞入 state。

### 保留手写项目，不就地重构

`agent-mini` 是你能解释底层机制的证据。`support-agent` 是另一个业务项目，用框架缩短交付并表达长任务。两者不共享 Agent runtime 代码，只能共享已稳定的协议思路和工程经验。

## 3. 落地执行

### Session 1（~2h）：建立框架映射基线

- 选取 `agent-mini` 的 tool loop、routing 和 evaluator-optimizer 三段已完成代码。
- 为每段列出 input、state、终止条件、错误、checkpoint 和观测点。
- 先口述手写版，再读官方文档，避免用框架名词覆盖原理。
- **完成标志**：不看框架文档也能讲清这三段手写代码的控制流。

### Session 2（~2h）：创建 `support-agent` 最小工程

- 新建 Python 3.12 + `uv` 项目，仅安装 LangChain v1、LangGraph、模型 provider、Pydantic settings 和 pytest。
- 建立 `src/support_agent/{config,models,tools,graphs,services}` 边界；不创建 DB、API 和 frontend 代码。
- 模型 ID、API key、timeout 和单 run 费用上限从 settings 注入，不在 graph node 中读环境变量。
- **完成标志**：一条命令能运行最小 model invoke，目录不包含后续周次的预留空抽象。

### Session 3（~2h）：LangChain model / tool / structured output

- 实现一个只读 `lookup_ticket_policy` 工具，工具输入和结果均有明确类型。
- 实现 `TicketClassification`：`category`、`priority`、`needs_clarification`、`reason`，通过 structured output 校验。
- 用 `create_agent` 运行一个只读小任务，观察消息、tool call、tool result 和终止条件。
- **完成标志**：能指出 `create_agent` 中哪部分对应 W3 loop，哪些业务规则仍需自己实现。

### Session 4（~2.5h）：用 LangGraph 重写一个旧 workflow

- 重写 W5 routing 或 evaluator-optimizer，二选一，不两个都写。
- state 使用 `TypedDict`，每个 node 只返回它修改的字段；循环必须有硬上限。
- 运行与手写版相同的固定输入，对比结果、模型调用次数、可读性和调试成本。
- **完成标志**：框架版结果与手写版业务等价，并保留一个已知失败输入用于对比。

### Session 5（~2h）：对照、反思与小型验收

- 用一张表总结“手写代码 / 框架 primitive / 框架收益 / 新的失败模式”。
- 回答为什么企业工单 Agent 使用 LangGraph，而 coding agent 仍保留手写 loop。
- 用 5 个固定输入检查分类结构化输出和框架 workflow，记录一个失败 trace。
- **完成标志**：能做 5 分钟框架对照口述，不使用“框架更方便”这种空泛结论。

### Session 6（P1，~2h）：SDK 横向对照

- 只读 Claude Agent SDK 和 OpenAI Agents SDK overview，对照 loop、tool、handoff/subagent、guardrail 和 trace。
- 不写第三份实现，只补充“什么业务前提会让我选它”。

## 4. 自测题

## 6. 常见坑速查

- **从组件大全开始学**：表现是记住大量 loader/chain 名字，但无法设计业务 state。回到映射表，只学主项目需要的 primitive。
- **在 node 里新建 client**：导致不可测、连接泄漏和配置散落。由 graph factory / service 注入依赖。
- **state 放所有东西**：导致 checkpoint 巨大、无法序列化。只放恢复执行必需数据和稳定 ID。
- **框架版没有同输入对照**：只看“跑通”无法判断行为是否回归。固定输入、模型和评价方式。
- **边看旧教程边猜 API**：以当前官方 v1 文档为唯一框架来源。

# W14｜LangGraph 企业业务编排

> **一句话目标**：实现“工单分类 → 检索占位 → 生成回复 → 风险分级”的 typed `StateGraph`，混合确定性节点与 LLM 节点，并将框架 streaming 适配为稳定的应用事件。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W13 框架映射验收通过。

## 1. 核心要掌握

### 先画状态转移，再写 node

P0 图固定为：

```text
START
  → normalize_ticket                   # 确定性
  → classify_ticket                    # LLM structured output
  → [needs clarification?]
      ├→ build_clarification → finalize
      └→ response_subgraph
           → retrieve_policy_stub       # 本周是内存固定资料
           → draft_response             # LLM
           → assess_risk                # 代码规则 + LLM structured output
           → finalize
  → END
```

W14 不接 PostgreSQL、pgvector 和 `interrupt()`：

- 检索节点先从固定的小型 policy corpus 返回 1–3 条证据。
- 高风险只输出 `requires_approval=True`，不暂停图；W15 再替换为真实 human-in-the-loop。
- 本周只证明业务流程和 state 设计正确，不同时学习基础设施。

### `TicketAgentState` 的边界

P0 字段：

- 标识：`organization_id`、`user_id`、`ticket_id`、`run_id`、`thread_id`。
- 输入：`subject`、`description`、`customer_tier`。
- 理解：`normalized_text`、`category`、`priority`、`missing_fields`。
- 证据：`evidence_refs`，只放小型引用对象，不放整篇文档。
- 输出：`draft_response`、`risk_level`、`risk_reasons`、`requires_approval`。
- 控制：`status`、`error_code`、`error_message`。

`TicketClassification`、`RiskAssessment` 和 `EvidenceRef` 使用 Pydantic 验证；graph state 使用 `TypedDict`。

### 确定性和 Agentic 节点要分开

- 空白裁剪、字段校验、状态映射、风险硬规则和最终输出组装用代码。
- 意图分类、自由文本理解、回复草稿和无法穷举的语义风险使用 LLM。
- 硬风险规则先于 LLM 判断；模型不能把“修改账户 / 退款 / 删除数据”降级为低风险。

### 应用事件与框架事件分层

LangGraph `astream_events` 是内部观测源，不是前端 API。用 `GraphEventAdapter` 转成下列稳定事件：

- 沿用现有 `text`、`tool_call`、`tool_result`、`context_usage`、`done` 的语义和公共 envelope。
- `status`：开始/结束某业务节点，只暴露稳定业务阶段名。
- `retrieval`：检索证据摘要和引用 ID。
- `diff`：保留为共享协议能力，工单 Agent 无文件变更时不产生。
- `approval_required`：本周只保留 schema，W15 启用。

不向 UI 暴露 chain-of-thought、完整 prompt、SDK message 或框架内部 node path。

## 3. 落地执行

### Session 1（~2h）：冻结业务状态与图

- 按本文定义实现 `TicketAgentState`、`TicketClassification`、`RiskAssessment`、`EvidenceRef`。
- 为每个 node 列出读字段、写字段、错误代码和是否调模型。
- 列表字段默认覆盖；只有事件/审计类数据才允许追加 reducer。
- **完成标志**：不运行模型就能用一个手造 state 走完所有确定性 node。

### Session 2（~2h）：分类与澄清分支

- `normalize_ticket` 负责校验和标准化；`classify_ticket` 只返回 structured classification。
- 分类限定为 `billing | account | product | technical | other`，priority 限定为 `low | normal | high | urgent`。
- `needs_clarification=True` 时进入 `build_clarification`，输出精确问题，不继续猜测。
- **完成标志**：8 个样例中，信息缺失输入均不进入回复生成子图。

### Session 3（~2.5h）：回复子图与风险路由

- 实现固定 policy corpus 与 `retrieve_policy_stub`，返回带 `source_id/title/snippet` 的证据。
- `draft_response` 必须只使用 state 中的 evidence，输出中包含引用 ID。
- `assess_risk` 先执行硬规则，再调模型评估语义风险；取两者更高级别。
- 将三个 node 封装为 `response_subgraph`，父图只传它需要的 state 字段。
- **完成标志**：“查询帐单”走低风险，“代我退款”必须输出 `requires_approval=True`。

### Session 4（~2h）：streaming 适配层

- 实现应用级 `AgentEvent` envelope 和 `GraphEventAdapter`，对框架事件做 allowlist 映射。
- 每条应用事件带 `run_id`、自增 `sequence`、`event`、`occurred_at`、`data`。
- 框架版本、node 函数名和 provider 原始消息不进入公开 schema。
- **完成标志**：命令行运行一个工单时可按序看到 `status/retrieval/text/context_usage/done`，最后一条恒为 `done`。

### Session 5（~2h）：固定用例与失败分类

- 建立 12 个工单 fixture：5 类工单、2 个缺信息、2 个高风险、1 个超长输入、2 个无关/模糊输入。
- 客观校验 graph 路径、structured output schema、硬风险规则和事件终态。
- 将失败分成分类、澄清、证据使用、风险与协议五类，只修最大的一类。
- **完成标志**：12 个 fixture 可一键运行，不用 UI 人工点击作为验证。

### Session 6（P1，~2h）：模型路由实验

- 用便宜模型执行 classification/risk，主力模型生成 draft，对比 12 case 的质量、成本和延迟。
- 只有数据证明总成本降低且 P0 行为不回归时才保留 router。

- [ ] `TicketAgentState` 可序列化，不包含 client/session/callback/完整文档。
- [ ] 确定性 node 与 LLM node 分开，structured output 均通过 Pydantic 校验。

## 6. 常见坑速查

- **先写 node 后补 state**：导致节点相互依赖隐式字段。先冻结 state 和每个 node 的读写集合。
- **所有步骤都调模型**：成本高且不可预测。字段校验、状态映射和硬规则用代码。
- **LLM 直接决定副作用**：W14 只产出风险结果，W15 必须加 interrupt 才能写外部系统。
- **把内部 stream 当公共 API**：框架升级会直接冲击前端。用 adapter 只暴露业务事件。
- **subgraph 共享全部 state**：边界形同虚设。子图只读写回复生成所需字段。

# W15｜持久化 + Human-in-the-loop + 幂等副作用

> **一句话目标**：让高风险工单在 `interrupt()` 处可持久暂停，服务重启后用同一 `thread_id` 恢复，并保证审批后的模拟 CRM 写入即使节点重放也只执行一次。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W14 业务图和风险分支验收通过。

## 1. 核心要掌握

### Checkpointer、Store 和业务数据库是三种责任

| 机制 | 保存什么 | 用于 | 不用于 |
|---|---|---|---|
| LangGraph checkpointer | 某 `thread_id` 的图状态快照 | 断点续跑、interrupt、故障恢复 | 工单列表、报表、多租户业务查询 |
| LangGraph store | 跨 thread 的应用记忆 | 用户偏好、可控长期 memory | 企业知识文档和交易性业务数据 |
| 业务 PostgreSQL | ticket/run/approval/tool action/audit | API 查询、权限、审计和业务一致性 | 代替图的完整 checkpoint |

W15 只引入支撑 checkpointer 和幂等 demo 的最小 PostgreSQL schema；完整业务 repository 和 migration 边界在 W20 完善。

### `interrupt()` 是状态边界，不是 UI confirm

- `approval_gate` 根据 state 中的草稿、风险、预期工具和参数组装 JSON-serializable payload。
- `interrupt(payload)` 暂停图；审批 API 使用同一 `thread_id` + `Command(resume=decision)` 恢复。
- decision 固定为 `approve | reject | revise`，`reject/revise` 需要 `feedback`。
- 恢复时 node 可能从开头重放，所以 interrupt 前的外部副作用不可依赖“代码看起来只跑一次”。

### Durable execution 不自动保证 exactly once

LLM 调用、发邮件、更新 CRM、扣款等都是不确定或外部副作用。W15 使用模拟 CRM，但必须使用真实幂等模式：

```text
idempotency_key = hash(organization_id, ticket_id, run_id, action_type, canonical_payload)
```

- `tool_actions.idempotency_key` 有唯一约束。
- 执行前尝试创建 `pending` action；已有 `succeeded` 则直接返回之前结果。
- 外部调用成功后写 `succeeded + result`；未知结果不盲目自动重试，先查外部系统或进入人工核对。
- 学习目标是 effectively-once，不宣称分布式 exactly-once。

### 审批必须绑定被审批的内容

审批记录保存 `proposal_hash`（草稿 + 工具名 + canonical arguments 的 hash）。恢复前重新计算；若与审批时不一致，原审批失效，必须再次审批。这防止“用户批准 A，系统执行 B”。

## 3. 落地执行

### Session 1（~2h）：checkpointer 与 ID 边界

- 本地启动 PostgreSQL，将 graph compile 从内存 saver 换成 async PostgreSQL checkpointer。
- 为 `ticket_id/run_id/thread_id` 各生成不同 UUID，通过 config 传 `thread_id`，不使用工单 ID 充当 thread ID。
- 打印 checkpoint 快照摘要，验证 state 无不可序列化对象。
- **完成标志**：进程退出重启后，同一 `thread_id` 能读到图状态。

### Session 2（~2.5h）：审批暂停与三分支恢复

- 将 W14 的 `requires_approval` 分支接到 `approval_gate`，低风险跳过，高风险调 `interrupt()`。
- 实现 approve/reject/revise：approve 进工具节点；reject 结束且不执行工具；revise 带 feedback 回到 draft，最多 2 次。
- 恢复必须使用同一 `thread_id`，同一个 approval 不能提交两次。
- **完成标志**：三个决策分支均有固定用例，重启服务后 approve 仍能继续。

### Session 3（~2h）：最小审批与工具行为存储

- 建立 `approvals` 和 `tool_actions` 最小表，暂不建完整 ticket repository。
- approval 保存 actor、decision、feedback、proposal_hash、decided_at；tool action 保存 idempotency key、status、request/result 摘要。
- 对 approval 和 idempotency key 建唯一约束，不只在 Python 中先查再写。
- **完成标志**：并发提交两次相同审批时，数据库只接受一条有效决策。

### Session 4（~2.5h）：模拟 CRM 幂等工具

- 实现 `update_crm_ticket`，只写本地模拟 CRM 表/适配器，不对接真实外部系统。
- 在工具执行成功后、node 返回前注入一次崩溃，恢复 graph，验证工具不会再写。
- proposal hash 改变时必须重新 interrupt，不复用之前的 approve。
- **完成标志**：故障注入后 CRM 记录只变化一次，并能指出保证来自 DB 唯一约束而不是内存 flag。

### Session 5（~2h）：恢复与重放测试集

- 覆盖：interrupt 前重启、interrupt 后未审批重启、approve 后工具前崩溃、工具后崩溃、重复 approve、改稿后旧 approve。
- 检查图终态、approval 记录、tool action 次数和模拟 CRM 最终值。
- 记录一条“市面上常见的 resume demo 为什么不等于生产安全”的口述答案。
- **完成标志**：上述故障场景可重复执行，无重复副作用。

### Session 6（P1，~1.5h）：Store 概念实验

- 用内存 store 保存一个用户回复语言偏好，用两个 thread 验证跨会话。
- 实验完成后不强行纳入 P0 项目；主项目 memory 需求由真实业务决定。

## 5. 验收 checklist

- [ ] PostgreSQL checkpointer 生效，服务重启后可按 `thread_id` 恢复。
- [ ] approve/reject/revise 三分支可重复运行，revise 最多 2 次。
- [ ] approval 与 tool action 都有 DB 唯一约束，不依赖内存 flag。
- [ ] proposal 改变会使旧审批失效。
- [ ] 工具成功后注入崩溃再恢复，模拟 CRM 仍只写一次。
- [ ] 六类暂停/恢复/重放场景有固定验证。

## 6. 常见坑速查

- **把 `InMemorySaver` 当生产持久化**：进程重启即丢失。W15 P0 必须用 PostgreSQL checkpointer。
- **interrupt 前先发邮件/改 CRM**：重放会重复执行。副作用放审批后，并且仍需幂等。
- **用“先查后写”实现幂等**：并发下仍重复。使用 DB 唯一约束 + 事务。
- **approve 不绑定内容**：草稿变更后仍执行旧审批。校验 proposal hash。
- **把 checkpoint 表直接当业务 API**：内部 schema 被 UI 耦合。业务 run 投影与图 state 分开。

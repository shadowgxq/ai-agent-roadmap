# W16｜Planning Agent：显式计划与任务分解

> **一句话目标**：让 Agent 先建立可执行的 `Plan`，再按步骤执行、验证和有限次重规划，而不是每轮只凭聊天上下文决定下一步。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W15 持久化、HITL 与副作用幂等验收通过。

## 1. 核心要掌握

### Reactive 与 Planning 的边界

```text
Reactive：Goal → LLM → Tool → Result → LLM → ...
Planning：Goal → Planner → Plan State → Executor → Verifier → Continue / Re-plan
```

- Reactive Agent 每轮选择下一步，适合短、低风险任务。
- Planning Agent 先形成中期任务结构，适合需要多次工具调用、验证和恢复的任务。
- 不为简单问答强行 planning；先建立 single-step baseline，再用任务复杂度决定是否启用 planner。

### Plan 是 State，不是回答文本

```python
class PlanStep:
    id: str
    description: str
    status: Literal["pending", "running", "completed", "failed"]
    dependencies: list[str]
    evidence_refs: list[str]

class AgentPlan:
    goal: str
    steps: list[PlanStep]
    version: int
```

- Plan、当前步骤、步骤结果和重规划次数必须可序列化并进入 checkpoint。
- `Planner` 只负责建立/更新计划，`Executor` 负责执行当前步骤，`Verifier` 负责用证据判定完成。
- Planner 不能覆盖已经完成的事实；变更计划要增加 `version` 并保留原因。

### 计划不是模型的自由发挥

- 用 structured output 校验步骤 ID、状态、依赖和完成条件。
- 代码检查依赖是否成环、是否引用不存在的步骤、是否超过步骤/成本预算。
- 计划最多允许 3 次 re-plan；超过上限进入 `blocked` 或人工介入，不无限循环。

## 3. 落地执行

### Session 1（~2h）：Reactive baseline 与任务分类

- 为 `advanced-coding-agent` 建立一个不带 planner 的 baseline：读取仓库、执行一个工具、输出结果。
- 准备简单任务（查找文件、解释函数）与复杂任务（定位并修复 bug、运行测试）。
- 记录工具调用数、成功率和是否出现重复工作，定义启用 planning 的门槛。
- **完成标志**：能解释同一目标在 Reactive 与 Planning 两种控制流中的差异。

### Session 2（~2h）：Task decomposition

- Planner 接收 `goal`、约束和可用工具，输出结构化 `AgentPlan`。
- 用“修复用户登录失败”作为固定 case，至少拆成定位入口、检查调用链、修改根因、运行测试四步。
- 用 schema 和代码校验步骤 ID、依赖、完成条件，不把漂亮 Markdown 当作计划。
- **完成标志**：10 个 case 中，复杂任务有可执行计划，简单任务可明确跳过 planning。

### Session 3（~2h）：Plan executor

- 将 `current_step`、`step_results`、`plan.version` 加入 graph state。
- Executor 每次只领取一个满足依赖的步骤，完成后由代码更新状态，不允许任意重写全量 Plan。
- 步骤结果保存摘要和 evidence ID，不把整段文件或 tool output 塞进 state。
- **完成标志**：中途 checkpoint 后恢复，能继续同一个步骤而不是重新生成一份计划。

### Session 4（~2h）：Step verification

- 为 coding task 接入确定性 verifier：文件变更存在、测试命令通过、目标条件满足。
- 对无法完全确定的语义结果使用 LLM verifier，但要求它引用 step evidence 并输出 `pass | fail | needs_review`。
- verifier 失败时进入 recovery，不允许仅凭“我觉得完成了”标记 `completed`。
- **完成标志**：故意制造测试失败，步骤保持 `failed`，不会错误结束整个任务。

### Session 5（~2h）：Re-plan 与预算

- 注入“根因不在原计划文件”的观察结果，触发 Planner 生成新版本计划。
- 只有证据表明计划无效时才重规划；保留旧版本、触发原因和受影响步骤。
- 增加 `max_replans=3`、最大步骤数、工具调用预算和总运行时预算。
- **完成标志**：计划失效会重规划，计划仍有效时不会无意义重规划；超过预算能进入 `blocked`。

### Session 6（P1，~1.5h）：规划策略对照

- 对照一次性 plan、逐步 plan 和 planner-executor 两种实现。
- 只保留有数据证明能提升成功率或可解释性的策略，不为展示而增加复杂算法。

## 6. 常见坑速查

- **把计划当 Markdown**：无法恢复、统计和校验；计划必须是 typed state。
- **Executor 重写全量计划**：职责混乱且容易丢失已完成事实；只更新当前步骤结果。
- **让 LLM 自报完成**：接入命令、文件或测试 verifier，再决定状态。
- **每轮都重新规划**：只有观察改变了任务假设才触发 re-plan，并设置硬上限。

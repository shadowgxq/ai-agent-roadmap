# W16｜企业 RAG：混合检索、引用与评估

> **一句话目标**：将 W14 的固定 policy corpus 替换为可入库的企业知识库，完成 PostgreSQL + pgvector + Full Text Search 混合检索、租户 metadata filter、引用溯源和至少 50 条 retrieval eval。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W15 暂停/恢复与副作用幂等验收通过。

## 1. 核心要掌握

### RAG 是检索系统，不是 prompt 技巧

P0 数据流：

```text
Markdown / text PDF
  → parse
  → structure-aware chunk
  → embed + tsvector
  → PostgreSQL / pgvector

ticket query
  → normalize / optional query rewrite
  → tenant + knowledge-base filter
  → vector top-k + FTS top-k
  → reciprocal-rank fusion
  → evidence refs
  → grounded answer with citations
```

一定要分开评估：

- **Retrieval eval**：期望文档/chunk 是否进 top-k，使用 Recall@K、MRR。
- **Answer eval**：回答是否被证据支持，引用是否指向正确文档片段。

检索失败时先改 chunk/query/filter/rank，不通过改生成 prompt 掩盖。

### P0 文档范围要克制

- 支持 Markdown、纯文本和有文本层的 PDF。
- 不做扫描件 OCR、表格理解、图像问答和网页爬取。
- chunk 优先按标题/段落边界，超长段落再按 token 切；保存 heading path、page、document version。
- 文档更新使用版本号：新版 chunks 完整就绪后再原子切换 active version，避免查到半套新旧数据。

### 多租户过滤必须在检索内完成

SQL 的 vector 和 FTS 分支都在查询条件中限制 `organization_id` 和 `knowledge_base_id`。不允许先跨租户取 top-k，再在 Python 中过滤：这既会泄漏数据，也会让当前租户的召回被其他租户结果挤掉。

### 引用是数据契约

`EvidenceRef` 固定包含：`chunk_id`、`document_id`、`document_title`、`document_version`、`heading_path/page`、`snippet`、`score`。

- 模型只能引用当次提供的 evidence ID。
- 服务端校验回答中的 citation ID 属于当次 evidence set；非法 ID 删除并记录失败。
- 没有足够证据时返回“无法从当前知识库确认”，不允许用模型常识补全企业政策。

## 3. 落地执行

### Session 1（~2h）：知识模型与版本化入库

- 建立 knowledge base、document、document version 和 chunk 的 domain model。
- chunk 带 tenant/KB/document/version/source location，embedding 与 `tsvector` 同时存储。
- 用 content hash 跳过内容未变的重复入库，新版本失败不影响 active version。
- **完成标志**：重复上传同文档不重复 embed，失败重建不破坏旧版检索。

### Session 2（~2.5h）：解析与结构化 chunk

- Markdown 保留 heading path；PDF 保留 page；清理页眉页脚重复文本。
- 先按标题/段落分割，超长块再用 token-aware splitter，相邻块保留少量 overlap。
- 选 10 个容易切错的样本：跨页段落、列表、代码块、长标题和短段落，人工审查 chunk。
- **完成标志**：chunk 不在标题与正文、列表项或代码块中间无意义断开。

### Session 3（~2.5h）：混合检索与 RRF

- 为同一 query 分别取 vector top-20 与 FTS top-20，两条 SQL 都先做 tenant/KB/active-version filter。
- 用 RRF 融合排名，P0 返回 top-5；保留 vector-only 基线作对照。
- 查询为空、纯停用词、超长、embedding 失败时有明确降级，最低可使用 FTS。
- **完成标志**：可对同一 query 打印 vector、FTS、fused 三组排名与过滤条件。

### Session 4（~2h）：retrieval eval 50 条

- 从自建企业 policy corpus 创建至少 50 条 query，每条标注一个或多个 relevant document/chunk。
- 覆盖同义改写、精确关键词、多条件问题、无答案问题和跨租户诱导。
- 输出 Recall@1/3/5、MRR 和 no-answer false-positive rate，对比 vector-only 与 hybrid。
- **完成标志**：hybrid Recall@5 达 0.80；未达标则本周顺延，不用 reranker 盲目遮盖数据/chunk 问题。

### Session 5（~2h）：引用生成与 answer audit

- 将 W14 retrieval stub 换成 hybrid retriever，draft prompt 只接收结构化 evidence refs。
- 服务端校验 citation ID，无证据时强制 abstain。
- 抽查至少 20 个回答，标注“引用支持了对应主张 / 指向正确位置”，计算引用正确率。
- **完成标志**：引用正确率达 90%，没有 evidence 外的伪造 citation ID。

### Session 6（P1，~2h）：reranker 对照

- 只在 top-5 主要失败来自排序而非召回时加 reranker。
- 只有 Recall@5/MRR 或引用正确率提升至少 5 个百分点，且延迟/成本可接受才保留。

## 5. 验收 checklist

- [ ] 支持 Markdown、纯文本和文本 PDF，文档版本可原子切换。
- [ ] chunk 保存 tenant/KB/document/version/source location，10 个边界样本已人工审查。
- [ ] vector 和 FTS 分支均在 SQL 内做 tenant/KB filter，使用 RRF 融合。
- [ ] retrieval eval 至少 50 条，hybrid Recall@5 ≥ 0.80。
- [ ] 至少 20 个回答引用抽查，正确率 ≥ 90%。
- [ ] 无证据问题会 abstain，无伪造 citation ID。

## 6. 常见坑速查

- **只看最终回答调 RAG**：无法区分检索失败与生成失败。先独立跑 retrieval eval。
- **chunk 只按字符数硬切**：标题、列表与政策条件被切断。优先结构边界，超长再 token split。
- **metadata 过滤放检索后**：既泄漏又降低当前租户召回。两条 SQL 分支内先过滤。
- **生成 prompt 允许模型补知识**：企业政策问答必须 grounded，无证据即 abstain。
- **一开始就加 reranker**：先用失败数据证明问题在 ranking，再做可归因实验。

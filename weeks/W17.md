# W17｜Long-horizon Agent：进度、上下文与恢复

> **一句话目标**：让 Agent 在几十次工具调用、上下文压缩、失败和服务重启之后，仍然知道目标、进度、证据和完成标准。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W16 Planning Agent 验收通过。

## 1. 核心要掌握

### Goal、Plan、Progress 和 Context 分层

```text
Goal
├── Constraints
├── Completion Criteria
├── Plan / Current Step
├── Completed / Failed / Blocked Steps
├── Evidence
├── Budget
└── Checkpoint
```

- `goal` 是跨会话稳定的任务目标，不等于一条用户消息。
- `graph state` 保存恢复当前执行所需的最小事实；`store` 保存跨 thread 的可控记忆；业务数据库保存查询、审计和交易数据。
- 每轮给 Agent 的上下文由 Goal、当前计划、进度和相关证据组成，不依赖无限增长的聊天历史。

### 长任务的完成必须可证明

```text
Goal → Completion Criteria → Deterministic / LLM Verifier → PASS / FAIL
```

- coding task 至少验证目标文件、测试、lint/build 或其他明确命令。
- 验证失败保持 `failed` 或 `blocked`，不能因为模型生成了“任务完成”而结束。
- 完成标准在任务开始时冻结；若需求变化，创建新 goal 或显式更新版本。

### 失败按责任分类

| 失败 | 常见处理 |
|---|---|
| tool failure | 按错误类型有限重试或 fallback |
| LLM failure | timeout、换模型或暂停 |
| step failure | 修正输入、回滚步骤或 re-plan |
| plan failure | 标记计划失效并重新规划 |
| infra failure | checkpoint 恢复、补偿或人工介入 |

`retry()` 不是通用的故障策略；外部副作用仍沿用 W15 的幂等和未知结果处理。

## 3. 落地执行

### Session 1（~2h）：Persistent goal 与完成标准

- 将 `advanced-coding-agent v1` 的输入拆成 `Goal`：objective、constraints、success criteria、created_at、version。
- 把成功标准转成可执行 verifier 清单，例如 pytest 通过、旧 API 保持兼容、目标文件已修改。
- 在 checkpoint 和业务 run 投影中分别保存 goal 摘要与状态，不复制整段聊天。
- **完成标志**：清空历史消息后，Agent 仍能仅凭 Goal 和 Plan 继续执行。

### Session 2（~2h）：Progress tracking

- 增加 `completed`、`in_progress`、`blocked`、`failed` 状态和每步 started/completed 时间。
- 每次工具调用都关联当前 step 和 evidence，不把没有归属的结果写进全局上下文。
- 输出 progress snapshot：当前步骤、已完成步骤、阻塞原因、剩余预算。
- **完成标志**：中断并恢复后不会重复已通过的步骤，也不会跳过未满足依赖的步骤。

### Session 3（~2.5h）：Context management

- 将上下文分为永久保留（Goal、约束、计划、关键决策）、可压缩（旧 tool result、旧 reasoning、大段文件）和按需恢复（代码、文档、RAG）。
- 使用 W07 的 compact 机制生成带 evidence 引用的摘要；原始内容按 ID 可重新读取。
- 设定 context budget，记录 compact 前后 token、恢复次数和丢失信息反馈。
- **完成标志**：连续执行 30 次工具调用后上下文不无限增长，且 verifier 仍能定位所需证据。

### Session 4（~2h）：Failure recovery

- 为 tool timeout、测试失败、计划失效、数据库断开和 worker 重启分别定义 transition。
- 对可重试错误使用指数退避和上限；对未知外部结果进入核对或人工介入，不盲目重放。
- 恢复时读取 checkpoint、业务 run 和 evidence，检查三者版本是否一致。
- **完成标志**：至少 5 类故障有不同处理路径，不会全部落入无限 retry。

### Session 5（~2h）：Completion verification

- 实现终态前的 completion gate，逐项运行 success criteria 并保存结果。
- 对语义验收使用带证据的 LLM verifier，输出 pass/fail/review 和理由摘要。
- verifier 未通过时回到对应步骤或 re-plan，只有全部标准通过才写 `succeeded`。
- **完成标志**：制造“代码改了但测试失败”和“测试通过但遗漏文件”两类 case，均不会错误完成。

### Session 6（~2h）：30–50 次调用长任务实验

- 运行一个包含仓库探索、修改、测试和一次 re-plan 的真实任务，目标 30–50 次工具调用。
- 记录 goal 偏离、重复工作、re-plan/compact 次数、checkpoint 恢复、token、成本、延迟和最终证据。
- 至少注入一次服务重启和一次工具失败，比较恢复前后的状态一致性。
- **完成标志**：形成第一条 Long-horizon eval，能解释失败发生在上下文、计划、工具还是基础设施。

## 4. 自测题

1. 为什么 user message 不能替代 persistent goal？
2. graph state、store、业务数据库分别保存什么？
3. context compact 后如何保证关键决策和证据可恢复？
4. tool failure、step failure、plan failure 为什么不能使用同一种 retry？
5. 什么条件满足后才允许写入 `succeeded`？

## 5. 验收 checklist

- [ ] Goal 包含 objective、constraints、success criteria 和版本，历史消息压缩后仍可执行。
- [ ] 进度状态、当前步骤、失败原因、evidence 和预算可查询、可恢复。
- [ ] compact 有 token/成本/信息完整性记录，原始证据可按 ID 恢复。
- [ ] 5 类故障有不同 recovery 策略，重试有上限且不重复外部副作用。
- [ ] 30–50 次工具调用实验完成，至少包含一次 re-plan、compact、重启和工具失败。
- [ ] completion verifier 阻止错误成功，Long-horizon eval 有可复核数据。

## 6. 常见坑速查

- **把完整聊天记录当长期记忆**：compact 后仍不可控；用 goal/progress/evidence 分层。
- **只保存当前步骤编号**：无法解释为何完成；保存状态、证据、版本和失败原因。
- **测试通过就结束**：还要验证 completion criteria 和目标范围，避免遗漏工作。
- **服务重启后从头跑**：用 checkpoint 恢复，并用幂等 action 防止重复副作用。
- **为了凑调用次数制造循环**：长任务实验应来自真实依赖、验证和恢复路径。

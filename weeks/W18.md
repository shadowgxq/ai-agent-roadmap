# W18｜Multi-Agent System：职责边界、路由与协作

> **一句话目标**：让多个有明确职责、工具和上下文边界的 Agent 协作，并用 single-agent baseline 证明拆分带来的收益值得成本。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W17 Long-horizon eval 通过。

## 1. 核心要掌握

### SubAgent 与 Multi-Agent 不是同一个概念

```text
SubAgent：Main → delegate → Subagent → Result → Main

Multi-Agent：Manager → Researcher / Coder / Tester → Results → Manager
```

- SubAgent 是单个主 Agent 的受限委派，适合封装一次局部能力。
- Multi-Agent 是多个职责边界明确的角色协作，通常包含 manager、路由、依赖和聚合。
- Multi-Agent 默认不是更好；先与 W17 的 single-agent baseline 比成功率、成本、延迟、工具调用和上下文 token。

### Worker 必须有真实差异

| 角色 | 责任 | 允许的上下文/工具 |
|---|---|---|
| Manager | 分解、分配、聚合、冲突处理 | Goal、Plan、各 worker 摘要 |
| Researcher | 搜索代码和证据 | 只读文件、检索工具 |
| Coder | 修改代码 | 受限写工具、当前 step |
| Tester | 运行测试并解释结果 | 测试命令、变更 diff |

Worker 使用不同 prompt、tools、context 和输出 schema，而不是复制三个相同 Agent。

### 路由与并行由依赖图决定

```text
Research A ─┐
Research B ─┼→ Manager aggregate → Coder → Tester
Research C ─┘
```

- 有依赖的步骤串行；无依赖且资源安全的步骤才并行。
- Manager 不应把所有原始上下文广播给所有 worker；只传目标、约束和最小证据。
- worker 结果必须带 evidence、status 和 recommendation，不能只返回自由文本。

## 3. 落地执行

### Session 1（~2h）：Single-agent baseline 与拆分决策

- 复用 W17 的 `advanced-coding-agent v2`，冻结一组相同 coding task 和模型/工具预算。
- 列出拆分的理由：上下文隔离、权限隔离、专业工具、可并行性或独立评估；没有理由的角色不创建。
- 画出 manager、worker、state 和 evidence 的数据流。
- **完成标志**：能对每个 worker 说明它解决的瓶颈，而不是只说“更高级”。

### Session 2（~2h）：Manager / Worker

- 实现 Manager：读取 Goal，生成任务分解，给 Researcher、Coder、Tester 分配带依赖的任务。
- 为每个 worker 固定 role prompt、输入/输出 schema、工具白名单和超时。
- worker 只返回结构化结果和 evidence 引用；Manager 决定是否接受、重试或改派。
- **完成标志**：一次完整任务能看到每个角色的输入、输出、状态和责任边界。

### Session 3（~2h）：Agent routing

- 将任务路由规则显式化：代码搜索 → Researcher，修改 → Coder，验证 → Tester。
- 先用确定性规则路由，再对无法穷举的任务使用 structured router；记录路由理由和 fallback。
- 路由失败进入 Manager recovery，不直接把任务丢给任意 worker。
- **完成标志**：10 个任务路由正确，未知任务有安全 fallback 和明确的失败原因。

### Session 4（~2.5h）：依赖图与并行执行

- 用依赖图标记可并行的只读研究任务，修改和测试保持串行。
- 限制并发数、单 worker 预算和总任务预算；聚合结果时按 task ID 去重。
- 注入一个 worker timeout，验证 Manager 可以等待、重试或改派而不重复写文件。
- **完成标志**：并行任务降低 wall-clock latency，且没有数据串租户、重复副作用或乱序覆盖。

### Session 5（~2h）：结果聚合与冲突处理

- 构造 Researcher 认为是缓存问题、Tester 认为是数据库问题的冲突 case。
- Manager 比较 evidence 和 verifier 结果，必要时发起追加调查，而不是随机选择一个答案。
- 聚合输出包含结论、证据、未解决冲突和下一步，不把互相矛盾的结论伪装成确定事实。
- **完成标志**：冲突会进入调查/人工 review；没有证据的 worker 结论不会直接触发写操作。

### Session 6（~2h）：Multi-Agent eval

- 对同一组至少 10 个任务比较 single-agent 与 multi-agent：success rate、cost、latency、tool calls、context tokens、failure rate。
- 分析并行带来的延迟收益、角色切换和聚合带来的额外成本。
- 只有在质量提升足以覆盖成本和复杂度时才保留 multi-agent；否则记录“不拆分”的工程结论。
- **完成标志**：形成一张对照表和一次可复述的架构取舍。

## 4. 自测题

1. SubAgent 与 Manager/Worker Multi-Agent 的边界是什么？
2. 什么条件下两个 worker 可以并行？
3. 为什么 worker 需要不同的 tools、context 和 output schema？
4. 两个 worker 结论冲突时，Manager 应依据什么决策？
5. Multi-Agent 比 single-agent 多花 4 倍成本时，什么数据能证明仍值得？

## 5. 验收 checklist

- [ ] `advanced-coding-agent v3` 有 Manager、Researcher、Coder、Tester 明确边界。
- [ ] 每个 worker 有独立 prompt、工具白名单、context 和结构化输出。
- [ ] 路由、依赖图、并发限制、超时和改派策略可观测。
- [ ] 至少一个无依赖研究阶段并行，依赖步骤保持串行。
- [ ] 冲突 case 经过 evidence comparison 或追加调查，不随机选结论。
- [ ] 与 single-agent baseline 完成 success/cost/latency/tool/token/failure 对照。

## 6. 常见坑速查

- **单 Agent 不会规划就先拆五个**：先通过 W16/W17 baseline，再证明拆分理由。
- **三个 Worker 只是改了名字**：职责、工具、上下文和 schema 必须真实不同。
- **所有任务并行**：依赖、写入和测试必须串行；并行只用于独立且安全的工作。
- **Manager 随机解决冲突**：比较 evidence，必要时追加调查或人工介入。
- **只看成功率**：同时报告成本、延迟、token、工具调用和维护复杂度。

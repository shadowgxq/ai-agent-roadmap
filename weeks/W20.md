# W20｜Agent 应用工程化：后端、安全与 React 业务闭环

> **目标**：将 W13–W19 的企业知识库与工单 Agent 集成为可运行的业务系统，完成「创建工单 → Agent 检索 → 风险判断 → 审批 → 工具执行 → 审计与回放」闭环。
> **投入**：建议累计 20–30h，按阶段验收而非固定一周。**前置**：W19 检索/引用评估通过，W15 审批恢复与写入幂等已验证。
> **方式**：以业务纵向切片推进；Codex 辅助常规工程实现，学习重点放在 Agent 专有运行机制及安全边界。

## 1. 核心要掌握

| 学习深度 | 内容 | 验收视角 |
|---|---|---|
| **必须理解** | `run_id` / `thread_id`、checkpoint 与业务状态、worker 重试/取消、外部副作用幂等 | 进程重启后恢复，写入不重复 |
| **必须理解** | Tool Permission、Prompt Injection 防护、Human-in-the-loop、租户数据边界 | 恶意文本与无权用户不能触发越权操作 |
| **必须理解** | SSE 持久化事件、`Last-Event-ID`、终态及前端回放 | 断线重连不重跑任务、不丢事件 |
| **直接复用** | CRUD、SQLAlchemy/Alembic、Redis/Celery、RBAC 基础、React/TanStack Query、Docker | 按既有工程规范交给 Codex 实现并验收 |

保留已有 `support-agent/` 和 `frontend/`，不新建独立前端、微服务或新的 Agent 框架；W19 的解析、Chunk、Hybrid Retrieval 直接接入，不重复实现。

**运行边界：**

```text
React（工单 / 时间线 / 审批 / 回放）
  ↕ REST + SSE
FastAPI（鉴权、租户上下文、幂等提交、事件查询）
  → PostgreSQL（工单、run 投影、事件、审批、审计）
  → Redis / Celery（任务调度）→ LangGraph + PostgreSQL checkpointer
      → W19 RAG → 风险分级 → interrupt
      → 审批通过 → 受控 MCP / 模拟 CRM（幂等写入）
```

- `ticket_id` 是业务对象，`run_id` 是执行实例，`thread_id` 是 checkpoint 游标；`organization_id` 只能来自已认证的服务端上下文。
- PostgreSQL 保存业务真相和持久事件；Redis 负责队列，不复制第二份业务状态；checkpoint 不替代 `runs` 表。
- 租户过滤下沉到 repository 和 W19 的检索 SQL；RBAC 管用户权限，Tool Policy 管 Agent 调用及参数，所有外部写入先走审批并记录审计。
- SSE 使用 `sequence` 去重与续传；`done` 才是终态，断线不是失败，UI 不展示内部推理内容。

## 3. 落地执行（端到端切片）

### Session 1：状态契约、数据库与租户上下文
- 复用 W15 checkpointer 与 W19 知识库 schema；补齐业务表、Alembic migration、索引/唯一约束、`Idempotency-Key`。
- 明确 `queued → running → waiting_approval → running → succeeded/failed/cancelled` 的合法迁移，审批与取消边界独立于队列状态。
- **完成标志**：迁移可重复执行，跨租户 ticket/document/run 读写均被拒绝。

### Session 2：异步 API 与持久 SSE
- 完成工单、run 创建与查询、取消、审批 API；请求快速返回 `202`，实际 Graph 在 Worker 运行。
- 用 `run_events` 保存带 `sequence` 的应用事件；断线通过 `Last-Event-ID` 补发，投递失败可由 outbox 或等价机制补偿。
- **完成标志**：重复请求不新建 run；Worker 重启后不丢 queued run 或终态事件。

### Session 3：受控工具与 Agent 安全
- 接入 `viewer/operator/approver/admin` 权限、服务端 tenant context、工具白名单/参数约束/审批策略。
- Agent 用 W19 EvidenceRef 生成带引用答复；CRM 写入必须有审批、唯一幂等键和可追溯审计。
- 对用户输入、RAG chunk、MCP 返回实施 Prompt Injection 防护；普通日志、trace、SSE 脱敏。
- **完成标志**：未审批写入与跨租户调用被拦截；重复审批/重试不会重复修改 CRM。

### Session 4：React 工单工作台
- 只扩展 `frontend/src/pages/support/`：工单列表/详情、检索引用、运行时间线、审批与审计。
- TanStack Query 管服务端数据，运行 Hook 管事件；`approve/reject/revise` 有提交中/错误状态，live 与 replay 共用时间线。
- **完成标志**：用户可完成完整工单流程；刷新、重连或重复事件不丢记录、不重复执行。

### Session 5：取消、恢复与并发
- 注入 Worker 崩溃、队列投递中断、LLM timeout、审批后重试及取消；写入未知结果不盲目重放。
- 并发提交至少 20 个 run，检查状态合法、`done` 唯一、`sequence` 无重复、租户数据隔离。
- **完成标志**：没有永久 queued、重复 CRM 写入、丢失终态或跨租户数据。

### Session 6：安全与产品验收
- 至少 15 条固定对抗用例覆盖用户输入、RAG、MCP 的恶意指令及无权操作，未审批外部副作用为 0。
- 验收登录、列表/详情、引用、审批/拒绝/修改、SSE 重连、历史回放及审计脱敏。
- **完成标志**：一条真实业务路径和故障路径均能复现，关键指标和失败证据可供 W21 复用。

## 6. 常见坑速查

- 用 FastAPI `BackgroundTasks` 代替持久队列：进程重启容易丢长任务；应有 Worker 和持久任务记录。
- PostgreSQL 与 Redis 都当业务真相：以 PostgreSQL 为准，Redis 只调度。
- 在 Python 中做跨租户结果后过滤：必须在 SQL / repository 层先过滤。
- 模型说“有权限”就允许写：服务端基于身份、工具策略、审批和参数再次校验。
- 把 SSE 连接结束当作业务终态：只信持久化 `done` 和 run 状态。

# W21｜鉴权、多租户与 Agent 安全

> **一句话目标**：为工单 Agent 加上可证明的身份、租户和工具权限边界，对 prompt injection、PII 和未审批副作用建立固定对抗 eval。
> **时间预算**：10–15h，5–6 个 session｜**前置**：W20 API、worker 与状态机验收通过。

## 1. 核心要掌握

### 身份与租户上下文

- 认证中间件从 HttpOnly cookie 解析 user，再从 membership 解析 organization_id 和 role。
- organization_id 只来自已验证的服务端上下文，不信任 body/query/header 中的租户参数。
- 每一个 repository 方法都显式接受 tenant context。
- worker 从持久化 run 记录还原 tenant context，不从用户输入重新推断。

### RBAC 与工具权限是两层

- RBAC 判断用户能否查看工单、上传文档、审批和取消。
- tool policy 判断 Agent 能否调用工具、允许的参数范围，以及是否需要人工审批。
- 工具白名单不能替代参数、租户校验与审计。

### 三类不可信文本

1. 工单用户输入。
2. RAG 检索块、文档内容、MCP 工具返回。
3. 模型生成的工具参数与自由文本。

所有不可信文本都作为 data 包装，不与系统策略同级；高风险操作不能只凭 prompt 保证。

### PII 与审计

- 日志、trace、SSE 不记录身份证、手机、邮箱、token 和 API key 原值。
- 审计记录 actor、tenant、tool、参数摘要、审批、结果、时间和 correlation ID。
- 原始敏感数据留在受限业务存储，不进入普通 trace 和前端。

## 3. 落地执行

### Session 1（~2h）：登录与身份上下文

- 实现演示用 login 与 HttpOnly cookie，不在 localStorage 保存访问 token。
- 中间件注入 CurrentUser、TenantContext 和 correlation ID。
- worker 只从数据库 run 记录还原上下文。
- **完成标志**：用户只能访问自己所属租户。

### Session 2（~2h）：RBAC 和资源授权

- 角色固定为 viewer、operator、approver、admin，每个路由声明所需权限。
- repository 强制接受 tenant context，缺失时拒绝查询。
- 构造跨租户 ticket/document/run 请求，期望全部拒绝。
- **完成标志**：租户约束覆盖列表、详情、SSE 和 approval API。

### Session 3（~2h）：MCP 工具策略

- 将 W8 MCP server 或模拟 CRM adapter 包成工具，区分读、写与危险操作。
- 工具注册表包含 permission、required_approval、timeout、idempotent 元数据。
- 调用前做服务端最终校验，不信任模型声称的 role/tenant。
- **完成标志**：viewer 可读不可写；写操作必须经过 approval gate。

### Session 4（~2h）：prompt injection 与 PII

- 分别在用户输入、检索 chunk、MCP result 中注入“忽略规则”“输出密钥”“执行删除”。
- 在系统策略、data wrapper、tool guard、approval 四层防护，不只修改 prompt。
- 实现统一 PII redact，覆盖日志、trace、SSE 和前端。
- **完成标志**：15 个对抗用例中未审批外部写入为 0，敏感值不进入前端和普通 trace。

### Session 5（~2h）：审计与安全回归

- audit_events 关联 ticket、run、approval、tool action。
- 检查日志不含 key、cookie、密码和完整 PII，但可按 correlation ID 回查。
- 把对抗用例加入常驻 eval。
- **完成标志**：每个失败可归因到鉴权、工具策略、数据包装、审批或脱敏。

### Session 6（P1，~1.5h）：通知边界设计

- 设计审批队列、操作与失败通知事件，不引入邮件/短信等新外部副作用。

## 4. 自测题

1. tenant context 为什么不能来自 body？
2. RBAC 与 tool permission 有什么关系和区别？
3. 工具白名单为什么不足以阻止未授权写操作？
4. RAG chunk 中的指令为什么不能与系统策略同级？
5. 为什么既要审计，又不能记录完整敏感输入？

## 5. 验收 checklist

- [ ] HttpOnly cookie 登录与 CurrentUser/TenantContext 就位。
- [ ] viewer/operator/approver/admin RBAC 与 tenant scope 有回归。
- [ ] 工具注册表有 permission/approval/timeout/idempotency 元数据。
- [ ] 15 个对抗用例通过，未审批副作用为 0。
- [ ] audit event 可按 correlation ID 回查，日志已脱敏。

## 6. 常见坑速查

- **只在路由层检查租户**：repository 或 worker 容易漏过滤；tenant context 必须下沉。
- **原始工具参数进入 trace**：统一 redact 后再上报。
- **把检索内容当指令**：外部文本都作为 data，工具层再次拦截。
- **worker 从用户输入推断 organization_id**：只从持久化 run 还原。
